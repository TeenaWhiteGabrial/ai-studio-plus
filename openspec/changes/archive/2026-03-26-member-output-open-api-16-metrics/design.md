## Context

当前 `member_output` 表结构：
- 4 个指标字段：prd_count、api_count、java_lines、frontend_lines
- 用于记录成员每日产出数据

目标：
1. 扩展为 16 个详细指标
2. 提供开放 API 接口，无需 token 认证
3. 通过 username 参数识别用户身份

## Goals / Non-Goals

**Goals:**
- 扩展 `member_output` 表至 16 个指标字段
- 提供开放 API 接口，无需 token 认证
- 通过 username 参数识别用户
- 支持每日数据更新（重复提交则更新）
- 保持现有数据兼容，不影响历史数据

**Non-Goals:**
- 不提供手工录入界面
- 不需要项目维度的统计
- 不需要自动扫描代码功能

## Decisions

### 1. 表结构扩展方案
**决策**: 在现有 `member_output` 表上新增字段，而非新建表
**理由**:
- 避免数据冗余，一套表就够了
- 保持按用户 + 日期的维度不变
- 历史数据兼容，新增字段默认值为 0

### 2. 接口认证方案
**决策**: 开放接口无需 token 认证，通过 username 参数识别用户
**理由**:
- 降低调用门槛，方便每个人自行提交
- 简化调用流程，不需要先在系统注册
- 假设用户会诚实提交自己的数据

**替代方案考虑**:
- 方案 A: 需要 token 认证 → 增加调用复杂度
- 方案 B: IP 白名单 → 维护成本高
- 方案 C: API Key → 需要预先分配，增加管理成本

### 3. 用户存在性校验
**决策**: 不校验 username 是否存在，允许任何 username 提交数据
**理由**:
- 简化接口逻辑
- 允许用户先提交数据，后续再关联到系统用户

### 4. 数据提交策略
**决策**: 同一用户同一天只能提交一次，重复提交则更新已有记录
**理由**:
- 避免数据重复
- 允许用户修正已提交的数据
- 使用 UPSERT 逻辑实现

## Risks / Trade-offs

**数据真实性风险** → 用户可能提交虚假数据或冒用他人 username
**Mitigation**: 建立信任机制，定期人工核对

**接口滥用风险** → 可能被恶意调用刷数据
**Mitigation**: 添加限流保护，同一 username 每天最多提交 N 次

**username 拼写错误** → 用户可能输错 username 导致数据无法关联
**Mitigation**: 返回提交成功提示时显示 username，让用户确认

**字段较多录入繁琐** → 16 个指标手动录入工作量大
**Mitigation**: 提供清晰的 API 文档和示例代码
