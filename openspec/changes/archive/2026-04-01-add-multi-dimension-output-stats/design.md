## Context

当前系统产出统计的数据模型已支持多维度数据存储（member_output 表包含 user_id, user_name, stat_date, project_root_name 及 16 项指标字段），但查询和展示层面仅实现了基础的时间维度和个人/全员维度。

用户表（sys_user）已通过 dept_id 关联部门表（sys_department），为部门维度统计提供了数据基础。项目维度通过 project_root_name 字段标识，无需额外项目表。

## Goals / Non-Goals

**Goals:**
- 实现部门维度统计：部门汇总、成员明细、部门排行
- 实现项目维度统计：项目汇总、成员明细、个人项目分布
- 增强时间筛选：固定周期（本周/本月/本季度/本年）+ 自定义范围
- 实现数据导出：Excel 格式导出所有统计结果
- 改造现有页面：增加筛选条件和导出功能
- 新增统计页面：部门统计、项目统计

**Non-Goals:**
- 不实现虚拟团队/跨部门协作组统计
- 不关联代码仓库自动识别项目
- 不实现滚动周期与自然月双模式
- 不实现节假日特殊处理
- 不实现热力图、趋势对比等深度可视化

## Decisions

### 1. 统计查询方式：SQL 聚合 vs 应用层聚合
**决策**: 使用 SQL 聚合查询
**理由**:
- 数据库层面聚合性能更好，减少数据传输
- 利用 MySQL 的 SUM、GROUP BY 等函数高效计算
- 避免应用层处理大量明细数据

**替代方案**: 应用层聚合（读取明细后在内存计算）
- 优点：灵活性高，可处理复杂逻辑
- 缺点：性能差，大数据量时内存压力大

### 2. 部门筛选：单选 vs 多选
**决策**: 支持多选（全选、单选、多选）
**理由**:
- 满足「查看所有部门排行」和「对比特定几个部门」两种场景
- 默认全选，方便查看整体情况

### 3. 项目筛选：单选 vs 多选
**决策**: 支持多选
**理由**:
- 个人视角可能需要查看自己在多个项目的产出合计
- 管理视角可能需要对比多个项目的产出情况

### 4. 导出实现：前端导出 vs 后端导出
**决策**: 后端导出（生成 Excel 文件提供下载）
**理由**:
- 大数据量时前端生成 Excel 性能差
- 后端导出可复用现有查询逻辑
- 支持异步导出（未来扩展）

**替代方案**: 前端导出（使用 SheetJS 等库）
- 优点：减少服务器压力
- 缺点：大数据量时浏览器卡顿

### 5. 索引策略
**决策**: 添加联合索引优化统计查询
```sql
-- 部门统计索引
ALTER TABLE member_output ADD INDEX idx_dept_date (dept_id, stat_date);

-- 项目统计索引
ALTER TABLE member_output ADD INDEX idx_project_date (project_root_name, stat_date);

-- 用户项目联合查询索引
ALTER TABLE member_output ADD INDEX idx_user_project_date (user_id, project_root_name, stat_date);
```

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|---------|
 数据量过大导致统计查询慢 | 1. 添加数据库索引优化查询性能<br>2. 限制单次查询最大时间范围（如一年）<br>3. 未来可考虑统计结果缓存 |
| 部门/项目维度数据权限问题 | 1. 当前实现不做复杂权限控制<br>2. 所有用户可查看所有部门/项目统计<br>3. 敏感数据场景未来再细化权限 |
| 导出大数据量导致内存溢出 | 1. 限制单次导出最大条数（如 10000 条）<br>2. 使用流式写入生成 Excel<br>3. 大数据量拆分为多个文件导出 |

## Migration Plan

1. **数据库迁移**：执行索引添加脚本（不停机，在线 DDL）
2. **后端部署**：新增接口上线（向后兼容，不影响现有功能）
3. **前端部署**：新页面和改造页面一起上线
4. **回滚策略**：如出现问题，可快速回滚前端，后端接口保留不影响现有功能
