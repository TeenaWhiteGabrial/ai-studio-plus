# GitLab 研发活动 AI 分析平台方案

## 1. 文档目的

本文档整理当前讨论结论，定义一个基于 GitLab 的研发活动 AI 分析平台的产品边界、端到端流程、AI 参与方式，以及产品形态建议。目标是将开发者日常代码活动自动转化为晨会看板、日报、周报、月报的依据。

## 2. 产品定位

该平台不是传统日报系统，也不是单纯的 GitLab 数据看板，而是一个以 GitLab 为主数据源、以 AI 大模型为核心分析引擎的研发活动理解平台。

平台核心目标：

- 自动理解开发者今天做了什么
- 判断当前工作推进情况
- 预测明日可能继续推进的内容
- 次日将预测与实际进行偏差比对
- 自动生成个人、小组、管理视角的晨会看板
- 自动沉淀日报、周报、月报

## 3. 核心边界

### 3.1 开发者日常行为边界

纳入核心流程的行为：

- 写代码
- 本地提交
- push 到 GitLab
- 创建或更新 Merge Request

不作为核心输入的行为：

- 回复 review 意见
- 关联 issue
- 触发 CI / pipeline
- 关闭 issue
- 发布或进入测试

额外约束：

- `commit message` 由 AI 自动生成，不要求开发者手写

### 3.2 GitLab 数据采集边界

采集对象保留：

- `users`
- `groups`
- `projects`
- `commits`
- `merge_requests`
- `branches`
- `members`

不采集对象：

- `issues`
- `comments/notes`
- `pipelines/jobs`
- `tags/releases`

### 3.3 AI 主导分析边界

以下步骤由 AI 大模型承担核心分析职责：

- 原始事件归并成工作项
- 进度判断
- 风险判断
- 阻塞判断
- 明日工作预测
- 次日预测偏差比对

结论：系统架构应采用“GitLab 事实采集 + AI 认知分析 + Web 展示与治理”的模式，而不是传统规则引擎为主的流程系统。

## 4. 端到端业务流程

整体流程分为 9 个阶段。

### 4.1 开发者写代码

开发者正常完成业务开发，不要求维护 issue、人工日报、工单补充说明等额外动作。

系统在本地提交前可感知的输入包括：

- 本次改动 diff
- 涉及文件路径
- 当前分支
- 所属仓库 / 项目
- 最近若干次提交上下文
- 是否已存在相关 MR

核心原则：

- 让 AI 从代码变化中理解工作内容
- 尽量减少开发者额外输入负担

### 4.2 AI 生成 commit message

开发者准备提交时，系统或 IDE 插件读取 staged diff，由 AI 自动生成 `commit message`。

AI 生成内容建议包括：

- 简洁版 commit message
- 可选详细说明
- 变更类型标签

典型输出示例：

- `feat: add team-based activity aggregation for morning dashboard`
- `fix: correct member grouping fallback in gitlab sync`
- `refactor: split daily summary generator from report pipeline`

该步骤的价值不仅在于优化提交体验，更重要的是为后续工作项归并、日报生成、明日预测提供稳定语义入口。

### 4.3 开发者提交并 push 到 GitLab

开发者确认 AI 生成的提交信息后完成：

- `git commit`
- `git push`

后续如果需要协作或阶段性收口，再创建或更新 MR。

### 4.4 开发者创建或更新 MR

系统采集 MR 的核心信息：

- MR 标题
- MR 描述
- 源分支 / 目标分支
- 创建时间 / 更新时间
- 作者
- 关联 commits
- 所属项目

在本系统中，MR 的主要价值是：

- 作为一组 commits 的工作主题容器
- 作为阶段性交付的边界线索
- 作为 AI 归并工作项的重要语义锚点

### 4.5 系统采集 GitLab 精简事件

采集方式建议并行使用：

- Webhook 进行实时增量采集
- 定时任务通过 GitLab API 进行补偿和历史回灌

采集后先落入原始事实库，并完成：

- 去重
- 标准化
- 时间线整理
- 用户、项目、分支、MR、commit 关联建立
- diff 摘要、文件路径特征保存

由于不接入 issue、评论、pipeline，后续分析对以下信息依赖更强：

- commit diff
- commit message
- MR 标题和描述
- 文件路径与模块知识
- 连续几天的提交轨迹

### 4.6 AI 将原始事件归并成工作项

这是第一层核心 AI 能力。

原始事实通常是碎片化的，例如：

- 一天内多个 commits
- 多次 push
- 一个或多个分支
- 一个 MR 的多次更新

AI 需要将这些碎片归并成“今天在做什么”的可读工作项。

归并时参考的主要信号：

- commit message
- diff 摘要
- 修改文件路径
- 提交时间序列
- MR 标题 / 描述
- 仓库模块知识
- 最近几天是否持续修改同一模块

归并后的工作项建议统一结构如下：

- 开发者
- 日期
- 工作项标题
- 工作项摘要
- 关联 commits
- 关联 MR
- 涉及模块
- 工作类型
- 证据摘要
- 置信度
- 所属项目
- 所属统计组

工作项归并的目标不是生成一句描述，而是完成研发活动的语义重建。

### 4.7 AI 判断进度、风险、阻塞

这是第二层核心 AI 能力。

由于不依赖 issue、review、pipeline，该步骤应从代码活动轨迹中推断研发状态。

#### 4.7.1 进度判断

AI 综合下列信号判断工作所处阶段：

- 是否仍有新 commit
- MR 是否已形成
- 改动主题是否在收敛
- 最近几天是否持续推进同一项工作
- 当前改动是探索型还是收口型

建议状态枚举：

- `started`
- `in_progress`
- `converging`
- `near_completion`
- `likely_completed`
- `uncertain`

这里的状态不是传统流程审批状态，而是 AI 推断的研发推进阶段。

#### 4.7.2 风险判断

风险判断主要关注代码行为模式，例如：

- 同一模块连续多次大改，说明方案可能不稳定
- 多日连续修改同一处但始终未形成收口，说明推进存在风险
- 高频碎片提交但主题发散，说明任务切换过多
- 单人同时跨多个项目推进，说明上下文负担高

#### 4.7.3 阻塞判断

在不采集评论、issue、pipeline 的前提下，阻塞更准确地说是“推进异常”识别。

典型信号：

- 昨天高频推进，今天突然停止
- 连续多日只有小修补，没有主题性推进
- 分支存在但迟迟不形成 MR
- 大范围改动后长期无后续动作
- 工作项长时间无法收敛

### 4.8 AI 生成明日工作预测

当天接近结束时，系统将近期工作轨迹交给 AI，预测开发者明日最可能继续推进的内容。

主要输入：

- 今日工作项
- 最近几天连续工作项
- 当前 branch / MR 状态
- 本次改动的收敛程度
- 开发者近期工作节奏
- 所属小组当前主主题

预测结果建议结构化输出：

- 预测内容
- 预测原因
- 置信度
- 关联证据
- 预测类型

预测类型建议包括：

- `continuation`
- `wrap_up`
- `expansion`
- `context_switch`

### 4.9 次日结束做预测偏差比对

次日结束后，系统拿“昨日预测”和“今日实际”活动进行语义比对。

输入：

- 昨日预测结果
- 今日新 commits / MR / branch 事实
- 今日 AI 新归并的工作项

AI 需要判断：

- 今日是否继续推进了昨日预测项
- 是完全命中、部分命中，还是明显偏离
- 偏离是自然扩展还是任务切换

偏差分类建议：

- `hit`
- `partial_hit`
- `shifted`
- `abandoned`
- `extended_scope`
- `uncertain`

该结果用于：

- 晨会回顾
- 日报中的偏差说明
- 周报/月报中的计划稳定性分析
- 后续模型优化

## 5. 晨会看板形成方式

看板形成逻辑分三层。

### 5.1 事实层

底层事实来源：

- commits
- branches
- merge requests
- users
- groups
- projects
- members

### 5.2 AI 认知层

AI 产出核心认知对象：

- 今日工作项
- 当前进度状态
- 风险 / 阻塞推断
- 明日工作预测
- 昨日预测偏差

### 5.3 展示层

展示层分三种视角：

#### 5.3.1 个人视图

展示内容：

- 今天主要在做什么
- 当前工作收敛程度
- 是否存在推进异常
- 昨日预测是否命中
- 明日最可能继续做什么

#### 5.3.2 小组视图

展示内容：

- 本组今天主要推进的主题
- 各成员当前主工作项
- 哪些工作存在风险或停滞迹象
- 小组明日重点预测
- 小组整体预测命中率

#### 5.3.3 管理视图

展示内容：

- 各组工作主题分布
- 哪些工作长期未收敛
- 哪些人或组存在明显发散
- 哪些主题在连续推进
- 周内整体趋势

晨会看板的本质不是事件列表，而是 AI 解释后的研发工作态势图。

## 6. 日报、周报、月报处理方式

### 6.1 日报生成

日报由系统在每天固定时间自动生成，支持个人日报和小组日报。

#### 6.1.1 个人日报

建议内容：

- 今日主要工作项
- 每项工作的摘要
- 当前进度判断
- 风险 / 阻塞判断
- 明日工作预测
- 与昨日预测的偏差说明

#### 6.1.2 小组日报

建议内容：

- 今日小组主要推进主题
- 主要成员工作分布
- 风险与停滞项
- 明日小组关注点
- 小组工作趋势摘要

日报生成链路：

GitLab 事实 -> AI 归并工作项 -> AI 判断状态 -> AI 生成自然语言日报 -> 存档 / 推送 / 导出

### 6.2 周报生成

周报不重新分析底层 commit，而是基于每天已生成的日报和工作项做二次总结。

处理逻辑：

1. 收集本周所有个人日报和小组日报
2. 合并重复工作项链路
3. 识别本周持续推进主题
4. 区分完成项、未完成项、发散项、停滞项
5. 由 AI 生成周度总结和趋势分析

周报重点：

- 本周核心推进主题
- 连续推进并收敛的事项
- 中途偏移的事项
- 持续风险主题
- 下周最可能继续推进的工作

### 6.3 月报生成

月报在周报基础上再做管理视角聚合。

链路：

日事实 -> 每日日报 -> 每周周报 -> 月度聚合 -> AI 生成月报

月报建议内容：

- 月度主要研发主题
- 各小组推进重心
- 持续时间最长的工作链
- 工作切换频率
- 收敛效率
- 风险与停滞趋势
- 预测命中率趋势
- 团队协作稳定性

月报重点是趋势和组织视角，而不是个人流水账。

## 7. 小组与统计视图

平台需支持灵活小组，而不是固定组织树。

建议支持：

- 按 GitLab group / project 自动归属
- 按业务线分组
- 按项目专项组分组
- 按临时协作组分组
- 一人属于多个统计组

统计视图至少包含：

- 个人视图
- 小组视图
- 项目视图
- 管理总览视图

## 8. 产品形态建议

结论：采用“网页平台 + 后台 Agent 体系”，不要只做 Agent，也不要优先做 App。

### 8.1 为什么不能只做 Agent

Agent 适合承担：

- GitLab 数据采集
- commit message 生成
- 工作项归并
- 进度 / 风险 / 阻塞判断
- 明日预测
- 次日偏差分析
- 日报 / 周报 / 月报生成

但 Agent 不适合直接承载：

- 晨会看板浏览
- 小组维度筛选
- 图表钻取
- 历史追溯
- 人工修正
- 权限管理

### 8.2 为什么不能只做网页

如果只有网页，没有后台 Agent 体系，会导致：

- GitLab 采集、AI 分析、报表生成都依赖同步触发
- 长耗时任务难以调度
- 次日偏差比对、周报月报聚合不稳定

因此后端必须具备异步任务和 Agent 化执行能力。

### 8.3 为什么 App 不是首选

App 适合轻量消费，不适合作为主工作台。

本系统核心场景包括：

- 浏览团队全景
- 看图表和趋势
- 筛选与对比
- 查看日报 / 周报 / 月报
- 配置统计组和治理规则

这些都更适合网页端完成。

App 可以作为后续补充能力，用于：

- 每日摘要通知
- 风险提醒
- 晨会前简报快速查看

### 8.4 推荐产品结构

建议拆成三层：

#### 8.4.1 Web 管理与展示平台

负责：

- 晨会看板
- 个人 / 小组 / 项目视图
- 日报、周报、月报查看
- 图表分析
- 灵活分组配置
- 权限管理
- 人工修正与审计

#### 8.4.2 后台 Agent 执行层

负责：

- GitLab 事件采集
- commit message 生成
- 工作项归并
- 进度 / 风险 / 阻塞判断
- 明日预测
- 次日偏差分析
- 日报 / 周报 / 月报生成

#### 8.4.3 消息触达层

负责：

- 飞书 / 企业微信 / 邮件推送
- 每日摘要
- 风险提醒
- 晨会前简报
- 周报 / 月报推送

## 9. AI 在整套系统中的角色

AI 不是附属摘要工具，而是核心分析引擎。

建议 AI 在以下环节承担主要职责：

- 提交前生成 commit message
- 理解 diff 和 MR 语义
- 将碎片事件归并成工作项
- 判断工作推进阶段
- 识别风险与收敛异常
- 预测明日工作
- 将昨日预测与今日实际做语义比对
- 生成日报、周报、月报自然语言内容

同时要保留基本原则：

- GitLab 原始事实是底座
- AI 负责语义解释和推断
- 展示结果应尽量关联证据链

## 10. 一句话总结

该平台应建设为一个以 GitLab 精简事实数据为输入、以 AI 大模型为核心认知引擎、以网页为主展示形态、以后台 Agent 为执行体系的研发活动分析平台。它从开发者提交代码开始，自动生成 commit message、归并工作项、判断进度与风险、预测次日工作、分析预测偏差，并最终产出晨会看板、日报、周报、月报。
