# AI Studio 测试 Fixture 与 AI 提示模板

## Fixture 约定

### 命名

- 浏览器 route mock 数据使用业务名命名，例如 `portal-article-list.json`。
- 后端契约测试数据直接写在测试类里，优先保持短小。
- 真实集成数据必须在文档中说明来源，不使用“数据库里刚好存在”的记录。

### 适用边界

- 页面结构、路由、空态、列表渲染：优先使用 route mock。
- 登录、权限、真实接口字段：使用真实后端或后端契约测试。
- 跨端业务流：必须有明确测试账号和可回收数据。

## Playwright 脚本生成提示

```text
请根据当前项目代码生成 Playwright 测试草稿。

约束：
1. 最终断言必须由 Playwright expect 完成，不让 AI 判断通过与否。
2. 如果不需要验证真实后端，请使用 page.route mock 固定响应。
3. 如果需要登录，必须通过环境变量读取账号密码，并在缺失时 test.skip。
4. 不要依赖不稳定的超长 timeout；优先使用 role、placeholder、text 等稳定选择器。
5. 不覆盖问答社区功能，当前测试重点是文章、资源、登录、后台/控制台主界面。

请输出：
1. 测试目标。
2. 需要的 fixture。
3. Playwright 代码草稿。
4. 可能的脆弱点。
```

## 后端契约测试生成提示

```text
请根据 Spring Boot DTO/controller 生成契约测试草稿。

项目规则：
1. 后端 JSON 合约以 snake_case 为准。
2. 不要优先连接数据库。
3. 优先测试 DTO 反序列化、Bean Validation、Result 响应包裹、关键字段命名。
4. 如果需要 MockMvc，优先 standaloneSetup 并 mock service。

请输出：
1. 覆盖的 API/DTO。
2. 为什么这是第一批高风险边界。
3. 测试代码草稿。
4. 仍需人工确认的业务语义。
```

## 失败分析提示

```text
下面是一次本地测试失败日志/截图/trace 摘要。请帮我分析。

要求：
1. 区分环境问题、测试数据问题、脚本问题、业务回归。
2. 给出最可能原因，不要编造没有证据的结论。
3. 指出需要查看的文件或命令。
4. 给出下一步最小验证动作。
5. 不要直接修改业务逻辑，除非失败证据明确指向业务 bug。
```
