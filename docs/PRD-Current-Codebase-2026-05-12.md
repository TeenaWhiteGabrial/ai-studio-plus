## 1. 文档目的

本文档用于基于当前代码现状，重建一份更适合团队协作的产品需求文档。
重构目标不是“把已有页面再描述一遍”，而是：

- 以业务能力为中心梳理系统
- 说清楚每项能力为什么存在
- 说清楚不同端分别承担什么职责
- 说清楚业务流程、状态流转、规则边界和验收口径

本文档描述的是**当前代码所体现出来的真实产品现状**，不是未来规划稿。

## 2. 产品概述

### 2.1 产品名称

AI-Studio

### 2.2 产品定位

AI-Studio 是一个面向 AI 团队协作、知识沉淀、内容生产、资源共享和平台治理的多端平台。

系统当前由以下几部分组成：

- Portal 门户端：内容入口、统一搜索、知识检索、文章与资源浏览
- Console 控制台端：成员工作台、内容创作、资源维护、任务与项目管理
- Admin 管理端：平台治理、资源审核、用户权限、消息配置、数据看板
- Knowledge 服务：独立知识库与检索服务
- 后端服务：为三端提供统一业务接口和认证能力

### 2.3 产品当前核心价值

从当前代码来看，AI-Studio 的核心价值主要体现在五个方向：

1. 为 AI 团队提供统一内容入口与知识访问入口
2. 为团队成员提供文章、资源、任务、项目等工作流支持
3. 为平台提供资源审核、组织权限、消息通知和站点配置能力
4. 为团队沉淀可复用的 Skill、Plugin、Tutorial、MCP 等资源资产
5. 为知识文档提供上传、索引和检索能力

## 5. 认证与账户体系

### 5.1 功能目标

为 Portal、Console、Admin 三端提供统一登录认证、用户信息获取和个人资料维护能力。

### 5.2 涉及角色

- 登录用户
- Console 用户
- 管理员

### 5.3 端职责分工

**Portal**

- 登录页入口
- 登录态判断
- 登录后进入搜索、文章、知识库和个人中心

**Console**

- 登录页入口
- 登录后进入工作台与个人工作流
- 个人设置页维护账号资料

**Admin**

- 登录页入口
- 登录后进入后台治理系统

**Common**

- 统一提供认证接口
- 提供 RSA 公钥、登录、获取 Token、获取用户信息、修改密码、更新个人资料、上传头像

### 5.4 关键流程

#### 流程 A：用户登录

1. 用户进入对应端登录页
2. 前端获取 RSA 公钥
3. 用户输入用户名和密码
4. 前端提交登录请求
5. 后端返回 Token 或登录响应
6. 前端保存登录态并跳转到目标页面

#### 流程 B：用户维护个人资料

1. 用户进入个人设置页
2. 修改密码或个人资料
3. 可上传头像
4. 系统保存更新结果

### 5.5 业务规则

- 三端共用统一认证能力
- 登录后通过 Token 维持会话
- 头像上传限制为图片类型，且大小受限
- 用户资料变更由当前登录用户自己发起

### 5.6 验收标准

- 用户可成功登录三端系统
- 登录后可获取当前用户信息
- 用户可修改密码
- 用户可修改个人资料
- 用户可上传头像

## 6. 文章内容生产与分发

### 6.1 功能目标

建立“创作 - 发布 - 浏览 - 互动 - 治理”的完整文章闭环，支撑平台内容沉淀与内容消费。

### 6.2 涉及角色

- Console 用户：创作和管理文章
- Portal 用户：阅读和互动
- Admin 管理员：治理和下架

### 6.3 端职责分工

**Console**

- 查看我的文章
- 创建文章
- 编辑文章
- 删除文章
- 立即发布文章
- 定时发布文章
- 取消定时发布
- 管理文章文件夹
- 管理文章标签

**Portal**

- 浏览文章列表
- 搜索文章
- 查看文章详情
- 点赞文章
- 评论文章
- 收藏文章

**Admin**

- 查看文章列表（管理视角）
- 查看文章详情（管理视角）
- 下架文章

### 6.4 关键流程

#### 流程 A：作者创建并发布文章

1. 用户在 Console 进入文章管理页
2. 创建文章，填写标题、正文、摘要、封面、文件夹、标签等内容
3. 用户选择：
   - 保存为待继续编辑内容
   - 立即发布
   - 定时发布
4. 系统保存文章并记录对应状态
5. 已发布文章可在 Portal 被检索和阅读

#### 流程 B：用户阅读并互动

1. 用户在 Portal 的首页、发现页或文章列表页进入文章
2. 查看文章详情
3. 进行点赞、评论、收藏等互动

#### 流程 C：管理员治理文章

1. 管理员在 Admin 查看文章列表
2. 选择文章并执行下架
3. 被下架文章不再作为公开内容展示

### 6.5 状态流转

根据当前代码可确认的文章状态至少涉及：

- 草稿/未公开
- 已发布
- 定时发布中
- 已下架
- 已删除

建议现阶段以以下产品语义统一：

- 草稿：作者可继续编辑，Portal 不可见
- 已发布：Portal 可见
- 定时发布中：尚未公开，待到时间自动发布
- 已下架：管理员已干预下线，Portal 不可见
- 已删除：逻辑删除或业务删除状态

### 6.6 业务规则

- 只有作者可以编辑和删除自己的文章
- Portal 文章列表仅展示已发布文章
- 点赞为切换式行为
- 定时发布时间必须为未来时间
- 下架文章后不应继续公开展示
- 文章创作端在 Console，消费端在 Portal，治理端在 Admin

### 6.7 验收标准

- 用户可在 Console 创建文章
- 用户可在 Console 编辑、删除文章
- 用户可立即发布文章
- 用户可设置定时发布并取消定时发布
- 已发布文章可在 Portal 列表中被检索和查看
- Portal 用户可对文章点赞
- 管理员可在 Admin 下架文章

## 7. 资源管理与发布

### 7.1 功能目标

为平台成员提供 Skill、Plugin、Tutorial、MCP 等资源的创建、维护、发布与使用能力，形成团队资源资产库。

### 7.2 涉及角色

- Console 用户：创建和维护资源
- Portal 用户：公开浏览部分资源
- Admin 管理员：管理与审核资源

### 7.3 资源范围

根据当前代码现状，重点资源类型包括：

- Skill
- Plugin
- Tutorial
- MCP

Portal 当前明确公开浏览的重点是：

- Skill
- Plugin
- Tutorial 的部分详情/下载能力

### 7.4 端职责分工

**Console**

- Skill 列表、详情、创建、更新、删除、发布版本、下载、上传文件
- Plugin 列表、详情、创建、更新、删除、发布版本、下载、上传文件
- Tutorial 列表、详情、创建、更新、删除、发布版本、上传附件
- MCP 列表、详情、创建、更新、删除、测试连接

**Portal**

- 公开浏览资源列表
- 查看资源详情
- 下载 Skill 和 Plugin
- 获取 Tutorial 视频地址和附件下载

**Admin**

- 查看资源列表与详情
- 审核 Skill、Plugin、Tutorial、MCP
- 管理资源版本
- 下载资源

### 7.5 关键流程

#### 流程 A：成员创建资源

1. 用户在 Console 进入资源中心
2. 创建资源主体信息
3. 上传资源文件或填写资源相关配置
4. 发布新版本
5. 资源进入平台资源体系

#### 流程 B：用户浏览资源

1. Portal 用户在发现页或资源页进入资源列表
2. 按类型、关键词、排序浏览
3. 查看详情并下载

#### 流程 C：资源版本更新

1. 资源拥有者在 Console 选择已有资源
2. 提交新的版本信息和资源文件
3. 系统记录版本历史

### 7.6 状态流转

当前资源体系至少涉及以下状态语义：

- 新建/待审核
- 审核通过
- 审核拒绝
- 已发布可见
- 已删除或不可见

### 7.7 业务规则

- Console 负责资源创作与维护
- Portal 只负责公开消费与下载
- 版本发布是资源管理中的核心动作
- 资源文件上传依赖 OSS
- 不同资源类型在详情和下载能力上存在差异

### 7.8 验收标准

- Console 用户可创建并维护资源
- Console 用户可为资源发布新版本
- Portal 用户可公开浏览部分资源
- Portal 用户可下载 Skill/Plugin，并访问 Tutorial 相关资源
- Admin 可查看并管理资源信息

## 8. 资源审核与治理

### 8.1 功能目标

为平台资源提供统一审核和治理能力，控制公开资源质量与可见性。

### 8.2 涉及角色

- OP_ADMIN
- SUPER_ADMIN

### 8.3 端职责分工

**Admin**

- 审核 Skill
- 审核 Plugin
- 审核 Tutorial
- 审核 MCP
- 记录审核意见
- 管理资源版本与部分删除能力

**Console**

- 作为资源提交端，等待审核结论

**Portal**

- 只展示满足公开条件的资源

### 8.4 关键流程

1. Console 用户创建或更新资源
2. 资源进入待审核状态
3. Admin 审核资源
4. 审核通过后，资源可按业务规则进入公开视图
5. 审核拒绝后，资源保持不公开状态，并可被修改后再次提交

### 8.5 业务规则

- 审核动作主要在 Admin 完成
- 审核结果决定资源是否能进入公开分发链路
- 审核意见应可记录和追踪

### 8.6 验收标准

- Admin 可查看待审核资源
- Admin 可对资源执行通过或拒绝
- 审核结果影响资源公开可见性

## 9. 知识库检索与管理

### 9.1 功能目标

为平台提供文档上传、向量索引和检索能力，支撑知识访问与知识运营。

### 9.2 涉及角色

- Portal 登录用户：知识检索使用者
- Admin 管理员：知识库维护者

### 9.3 端职责分工

**Portal**

- 提供知识库搜索页
- 检查知识库服务状态
- 提交搜索词和返回条数
- 展示检索结果片段

**Admin**

- 查看知识库统计
- 查看文档列表
- 上传文档
- 删除文档
- 重建索引

**Knowledge 服务**

- 提供健康检查
- 管理文档
- 提供搜索与统计

### 9.4 关键流程

#### 流程 A：管理员维护知识库

1. 管理员进入知识库管理页
2. 查看服务状态和统计
3. 上传文档或删除文档

#### 流程 B：用户检索知识

1. 用户进入 Portal 知识库页
2. 输入关键词或知识线索
3. 设置返回片段数量
4. 系统返回知识片段

### 9.5 业务规则

- Portal 侧知识库页当前需要登录
- 当前能力以“检索结果片段展示”为主，不是完整对话产品
- Knowledge 服务与主系统是独立服务关系

### 9.6 验收标准

- 管理员可维护文档
- Portal 用户可检索知识片段
- 系统可显示知识库服务状态

### 12.1 功能目标

为平台提供用户、角色、菜单、部门、团队等基础治理能力，支撑多角色、多组织的后台运行。

### 12.2 涉及角色

- SUPER_ADMIN
- OP_ADMIN
- DEPT_ADMIN

### 12.3 端职责分工

- 用户管理
- 角色管理
- 菜单管理
- 部门管理
- 团队管理
- 团队成员维护

### 12.4 关键流程

3. 分配角色

#### 流程 B：管理员配置角色权限

1. 管理员查看角色列表
2. 为角色配置菜单权限
3. 系统根据角色控制菜单可见性与功能可访问性

- 角色菜单配置能影响实际菜单展示
- 团队成员关系可维护

## 13. 接口与数据契约原则

### 14.1 契约格式

当前后端 JSON 契约以 `snake_case` 为主格式。
前端内部可使用 `camelCase`，但必须在 API 边界做显式映射。

### 14.2 接口分层

当前后端按以下前缀区分能力边界：

- `/auth/*`：认证与账户能力
- `/portal/open/*`：Portal 公开能力
- `/portal/*`：Portal 登录后能力
- `/console/*`：Console 工作台能力
- `/admin/*`：Admin 治理能力
- `/open/*`：开放接口能力
